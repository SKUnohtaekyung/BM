# 12주차 최종 세션 계획안

## 문서 기반 AI Agent 실습: 기획을 작동하는 화면으로 바꾸기

- 대상: 멋쟁이사자처럼 14기 기획/디자인 파트원
- 형식: 90분 개별 실습
- 도구: ChatGPT Go 기반 Codex, Google Antigravity
- 핵심 산출물: `prd.md`, `design.md`, Mock Data 기반 프론트 프로토타입
- 실습 주제: **교수님이 보면 한숨, 학생들은 박수칠 서비스**

---

# 1. 세션 한 줄 정의

AI Agent에게 문제, 사용자, 화면 구조, 디자인 기준, 제외 범위를 문서로 전달하고, 그 문서를 기반으로 Mock Data 프론트 프로토타입을 만들어보는 실습 세션.

---

# 2. 세션 핵심 메시지

AI를 잘 쓰는 기획자는 한 문장 요청에 의존하지 않고, Agent가 실행할 수 있는 맥락과 기준을 문서로 정리한다.

이번 세션에서 학생들이 가져가야 할 문장:

> 좋은 결과는 좋은 요청에서 시작한다.  
> 좋은 요청은 문제, 사용자, 구조, 기준, 제외 범위를 포함한다.

---

# 3. 세션 목표

## 3.1 파트원용 목표

학생들은 세션 종료 후 다음을 할 수 있어야 한다.

1. LLM과 Agent의 차이를 간단히 설명할 수 있다.
2. AI에게 작업을 요청할 때 맥락, 목표, 제약, 출력 형태, 검증 기준을 함께 줄 수 있다.
3. `prd.md`에 문제, 사용자, IA, User Flow, 핵심 기능, 제외 범위를 작성할 수 있다.
4. `design.md`에 화면 목록, 레이아웃, 컴포넌트, 문구 톤, 금지사항을 작성할 수 있다.
5. Codex가 만든 결과물을 PRD와 Design 기준으로 검토할 수 있다.

## 3.2 태경님 운영 목표

1. 1~6주차 기획 개념을 AI Agent 실습에 재사용하게 만든다.
2. 학생들이 AI를 단순 질의응답 도구에서 작업 실행 파트너로 인식하게 만든다.
3. AI 생성 결과를 그대로 믿는 습관을 줄이고, 검증 기준을 세우는 습관을 만든다.
4. DB, 백엔드, API, 배포 없이도 서비스 흐름을 프론트 프로토타입으로 표현하게 만든다.

## 8.2 LLM과 Agent의 차이

### 핵심 설명

| 구분 | LLM | Agent |
|---|---|---|
| 기본 역할 | 답변 생성 | 작업 수행 |
| 입력 | 질문, 지시 | 목표, 문서, 파일, 권한 |
| 결과 | 텍스트 중심 | 파일 생성, 코드 수정, 실행 결과 |
| 흐름 | 한 번의 응답 중심 | 계획, 실행, 수정, 검토 |
| 기획자 역할 | 질문을 잘 쓰기 | 작업 기준을 잘 넘기기 |

### 학생용 한 문장

LLM은 답을 주고, Agent는 파일을 읽고 고치며 작업을 진행한다.

### 용어 정리: 에이전틱 코딩 vs 바이브 코딩

공식 문서(OpenAI, Anthropic)가 일관되게 쓰는 용어는 **agentic coding / coding agent**다.
"바이브 코딩(Vibe Coding)"은 2025년 2월 Andrej Karpathy가 만든 비공식 신조어로, 결과를 깊이 검토하지 않고 받아들이는 사용 태도를 가리킨다. (근거: `리서치_세션근거.md` Q2)

세션 진행 시 원칙:
- 세션 제목·미션명에 쓰는 "바이브 코딩"이라는 표현은 자연스럽게 유지한다.
- 단, 이것이 업계 공식 개발 방법론인 것처럼 단정하지 않는다. 대놓고 "공식 용어가 아닙니다"라고 부정하지도 않는다.
- 필요하면 한 문장으로 자연스럽게 짚는다: "오늘 우리가 '바이브 코딩'이라고 부르는 이 방식을, 실무에서는 조금 더 정확히 'agentic coding(에이전틱 코딩)'이라고 부릅니다."

### 안전: 에이전트는 '말'이 아니라 '행동'한다

LLM은 틀려도 '틀린 답'이지만, Agent는 틀리면 '틀린 행동'(파일 수정·명령 실행·외부 연결)을 한다. 그래서 Codex·Antigravity는 상태를 바꾸는 작업 전에 **승인창**을 띄운다. 이 개념은 별도 시간 없이 LLM/Agent 구분 슬라이드에 이어 한 호흡으로 전달한다.

학생에게 전할 3가지:

1. 승인창은 **읽고** 누른다. 무엇을 하려는지 모르면 승인하지 않는다.
2. 비밀번호·API 키·개인정보를 프롬프트나 파일에 붙여넣지 않는다.
3. "모든 권한 허용 / 승인 건너뛰기"(danger-full-access, skip-permissions) 같은 모드는 켜지 않는다.

(근거: `리서치_세션근거.md` Q9 — 세 도구 모두 '기본 읽기 위주 + 상태 변경은 사람 승인 + 쓰기는 작업폴더 한정' 모델을 공유)

## 8.3 AI에게 일 잘 시키는 법

Context Engineering은 깊게 다루지 않고, 질문 팁으로 전달한다.

### 5요소

| 요소 | 질문 |
|---|---|
| 맥락 | 지금 어떤 상황인가 |
| 목표 | 무엇을 만들고 싶은가 |
| 기준 | 좋은 결과는 어떤 모습인가 |
| 제약 | 하지 말아야 할 것은 무엇인가 |
| 출력 | 어떤 형태로 받고 싶은가 |

> 최신 공식 가이드(OpenAI GPT-5.5·Anthropic Opus 4.8, 2026)는 **원하는 결과와 성공 기준을 먼저** 적는 outcome-first를 권한다. 5요소 중 **목표·기준(원하는 결과)을 앞세우고**, 과정을 너무 세세히 지시하지 않는 편이 최신 모델에 잘 맞는다. (근거: `리서치_세션근거.md` Q3)

### 예시

```text
나는 대학생 대상 프론트 프로토타입을 만들고 있어.
docs/prd.md와 docs/design.md를 읽고,
그 기준에 맞춰 mock data 기반 웹 화면을 만들어줘.
로그인, DB, 실제 API, 배포는 만들지 마.
결과를 만든 뒤 어떤 요구사항을 반영했는지 요약해줘.
```

## 8.4 문서의 힘: 막연한 요청 vs 문서 기반 요청 (라이트 데모)

문서가 왜 필요한지 말로 설명하는 대신 **결과를 나란히 보여준다**. 약 1분, 뒤이어 나올 `prd.md`·`design.md` 파트로 넘어가는 동기부여용.

- 왼쪽: 막연한 프롬프트("대학생용 앱 만들어줘") 결과 화면 캡처 1장
- 오른쪽: 같은 아이디어를 `prd.md`·`design.md`로 정의한 뒤 만든 결과 화면 캡처 1장

전할 문장: "같은 AI, 같은 아이디어인데 결과가 다릅니다. 차이는 요청의 구체성 — 그 구체성을 담는 게 문서입니다."

준비물: 사전에 두 방식으로 한 번씩 돌려 **결과 캡처 2장을 미리 확보**한다(라이브 생성 아님 — 시간 리스크 회피). (근거: `리서치_세션근거.md` §4 '문서 사용 vs 미사용 비교')

# 9. `prd.md` 구조

## 9.1 PRD의 역할

`prd.md`는 Agent에게 무엇을 왜 만들지 알려주는 요구사항 문서다.

이번 실습에서 `prd.md`는 1~6주차 개념을 하나로 묶는 문서 역할을 한다.

## 9.2 PRD 템플릿

```md
# PRD

## 1. 서비스 개요
이 서비스가 무엇인지 한 문장으로 작성한다.

## 2. 해결하려는 문제
대학생이 어떤 반복적인 불편을 겪는지 작성한다.

## 3. 핵심 사용자
이 서비스를 가장 먼저 사용할 사용자를 작성한다.

## 4. 핵심 시나리오
사용자가 어떤 상황에서 이 서비스를 쓰는지 작성한다.

## 5. IA / 화면 구조
이번 프로토타입에 필요한 화면과 각 화면의 역할을 작성한다.

예시:
- 홈 화면: 서비스 소개와 시작 버튼
- 입력 화면: 사용자가 조건을 입력하거나 선택
- 결과 화면: 추천 또는 정리 결과 표시
- 상세 화면: 선택한 항목의 구체 정보 표시

## 6. User Flow
사용자가 어떤 순서로 이동하는지 작성한다.

예시:
홈 → 조건 선택 → 결과 확인 → 상세 확인 → 처음으로 돌아가기

## 7. 핵심 기능
이번 프로토타입에 반드시 들어갈 기능을 작성한다.

## 8. 기본 상태
핵심 성공 흐름에서 각 화면이 어떤 상태로 보이는지 작성한다.
이번 실습에서는 예외 상태를 다루지 않는다.

## 9. 제외 범위
이번 실습에서 만들지 않을 것을 작성한다.

예시:
- 로그인
- 회원가입
- 실제 DB
- 실제 API
- 결제
- 지도
- 알림
- 배포

## 10. 완료 기준
어떤 결과가 나오면 완성으로 볼지 작성한다.
```

## 9.3 1~6주차 개념 연결

| PRD 항목 | 연결 개념 |
|---|---|
| 서비스 개요 | What |
| 해결하려는 문제 | Why |
| 핵심 사용자 | Who |
| 핵심 시나리오 | 사용자 상황 |
| IA / 화면 구조 | IA |
| User Flow | User Flow |
| 핵심 기능 | MVP |

# 10. `design.md` 구조

> **[웹서칭 검토 완료]** `design.md` 패턴은 유효하다 — AWS Kiro가 `requirements.md → design.md → tasks.md` 구조에서 `design.md` 파일명을 실제로 쓰고, '코딩 전 설계를 문서로 먼저 쓰는' 접근은 Spec-Driven Development(GitHub Spec Kit 등)로 정식 도구화돼 있다. 다만 §4.2대로 '업계 공식 표준 파일명'으로 단정하지 않는다. (근거: `리서치_세션근거.md` Q6)

## 10.1 Design 문서의 역할

`design.md`는 Agent가 일관된 화면을 만들 수 있도록 시각 기준과 문구 기준을 정리하는 문서다.

## 10.2 Design 템플릿

```md
# Design Guide

## 1. 디자인 목표
사용자가 이 화면에서 어떤 느낌을 받아야 하는지 작성한다.

예시:
빠르게 이해할 수 있고, 선택하기 쉬운 모바일 웹 화면

## 2. 화면 목록
PRD의 IA와 연결해서 필요한 화면을 작성한다.

## 3. 레이아웃 원칙
화면 배치 기준을 작성한다.

예시:
- 모바일 우선
- 상단에는 제목과 설명
- 본문에는 카드형 목록
- 하단에는 주요 CTA 버튼

## 4. 컴포넌트 규칙
버튼, 카드, 태그, 입력창 등의 기준을 작성한다.

## 5. 기본 상태 화면 기준
핵심 흐름에서 각 화면이 어떤 문구와 구조로 보여야 하는지 작성한다.

## 6. 문구 톤
사용자에게 보여줄 문장의 톤을 작성한다.

예시:
짧고 명확하게, 어려운 용어 사용 금지

## 7. 금지사항
사용하지 않을 디자인 요소를 작성한다.

예시:
- 과한 애니메이션
- 너무 많은 색상
- 복잡한 메뉴
- 작은 글씨
```

# 18. 진행 멘트 모음

## 오프닝

Design 문서는 화면의 일관성을 지키기 위한 기준입니다.  
Agent는 기준이 없으면 화면 분위기와 구성 요소를 임의로 정할 수 있습니다.

## 실습 시작

## 마무리

AI 시대의 기획자는 문제, 사용자, 화면 구조, 제외 범위, 검증 기준을 정리해 Agent가 실행할 수 있는 형태로 넘깁니다.
