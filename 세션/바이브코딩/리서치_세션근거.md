## 1. Executive Summary

### 핵심 결론 5
1. **LLM은 '부품', 에이전트는 '시스템'이다.** LLM은 다음 텍스트를 생성하는 모델이고, AI 에이전트는 그 LLM이 도구를 스스로 골라 쓰며 목표가 끝날 때까지 '도구 호출 → 결과 확인 → 다음 판단'을 반복(루프)하는 시스템이다. 차이는 모델 크기가 아니라 구조·자율성이다. (Anthropic, https://www.anthropic.com/engineering/building-effective-agents, 2024-12-19)
2. **에이전틱 코딩(agentic coding)은 공식 용어, 바이브 코딩은 유행어다.** OpenAI·Anthropic 공식 문서는 'coding agent / agentic coding'을 일관되게 쓰고, 'vibe coding'은 2025-02 Karpathy의 X 게시글에서 나온 비공식 신조어다. (IEEE Spectrum, https://spectrum.ieee.org/vibe-coding, 2025-04-08 / Anthropic, https://www.anthropic.com/research/claude-code-expertise, 2026-06-16)
3. **최신 프롬프트 기준은 '과정'이 아니라 '결과'를 먼저 적는 것.** OpenAI GPT-5.5 가이드는 outcome-first(결과·제약·출력형태 우선), Anthropic Opus 4.8 가이드는 '맥락 없는 신입에게 설명하듯' 명확·구체 + 긍정 예시(`<example>` 태그) + XML 구조를 권한다. 두 회사의 공통 뼈대는 지시·맥락·제약·형식·예시 + 작게 반복. (OpenAI, https://developers.openai.com/api/docs/guides/prompt-guidance / Anthropic, https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) ※ 두 가이드 '페이지'는 발행일 미표기이나, 대상 모델(GPT-5.5 2026-04-24·Opus 4.8 2026-05-28) 출시일 기준 창 내다.
4. **prd.md·design.md는 공식 필수 파일이 아니라 '코딩 전 명세를 먼저 쓰는' 검증된 실무 패턴(Spec-Driven Development)의 교육용 이름이다.** 도구가 자동으로 읽는 표준 파일은 AGENTS.md·CLAUDE.md·.cursor/rules뿐이며, prd/design 문서는 프롬프트로 지목하거나 @import해야 반영된다. (GitHub Spec Kit, https://github.com/github/spec-kit, 2026-07-07 / Microsoft Learn, https://learn.microsoft.com/en-us/training/modules/spec-driven-development-github-spec-kit-greenfield-intro/, 2026-07-03)
5. **에이전트는 '말'이 아니라 '행동'하므로 사람 검증이 필수다.** 파일 수정·명령 실행·외부 연결은 반드시 사람이 승인·검증해야 하며, 최근 실증연구는 AI 생성 코드가 취약점을 자주 포함하고 모델이 그 안전성을 과신함을 보고한다. (OpenAI Auto-review, https://alignment.openai.com/auto-review/, 2026-04-30 / arXiv, https://arxiv.org/abs/2606.31159, 2026-06-30)

### 이번 세션에 직접 반영할 내용 5
1. **prd.md = '무엇을·왜'(문제·타깃·핵심기능·성공기준), design.md = '어떻게 보이게'(화면 목록·IA·User Flow·상태·UI 기준)** 로 역할을 명확히 나눠 실습 뼈대로 삼는다. OpenAI Codex 프롬프트 4요소(Goal·Context·Constraints·Done-when)가 prd 뼈대와 1:1로 맞는다. (https://developers.openai.com/codex/learn/best-practices)
2. **초급자 프롬프트 6원칙**(①결과 먼저 ②맥락·이유 ③제약 명시 ④출력형식 고정 ⑤예시 제시 ⑥작게 시작해 반복)을 두 회사 공통 교집합으로 가르친다 — 도구(Codex/Claude/Antigravity)에 종속되지 않는다.
3. **안전 기본기**: 세 도구(Codex·Claude Code·Antigravity) 모두 '기본 읽기 위주 + 상태 변경은 사람 승인 + 쓰기는 작업폴더 한정'이라는 동일 모델을 쓴다. 이 기본값을 그대로 두고 승인창을 '읽고' 누르게 한다. (https://developers.openai.com/codex/concepts/sandboxing / https://code.claude.com/docs/en/security)
4. **검증 습관**: 프로토타입이 나오면 ①실행되나 ②주요 User Flow가 끝까지 되나 ③prd·design과 맞나를 사람이 직접 클릭·대조하게 한다(초급자용 검증 체크리스트).
5. **고급 기능은 '있다'만 소개하고 실습에서 뺀다**: AGENTS.md/CLAUDE.md/rules/hooks/skills/subagents/MCP 외부연결/인증·결제·DB·배포. OpenAI 공식도 이들을 '반복이 생긴 뒤·신뢰가 쌓인 뒤'의 후속 단계로 배치한다.

### 절대 말하면 안 되는 오개념 5
1. ❌ **"prd.md·design.md만 만들어두면 Codex/Claude가 알아서 읽는다"** — 자동 로드는 AGENTS.md·CLAUDE.md·.cursor/rules뿐. 일반 문서는 지목·import해야 반영된다.
2. ❌ **"에이전트가 승인을 안 물어보면 안전한 것"** — 승인 요청 부재가 안전을 뜻하지 않는다. 결과물은 사람이 직접 검증해야 한다. (OpenAI Auto-review 명시: 자동 리뷰는 '보안 보장이 아님')
3. ❌ **"프롬프트는 길고 단계가 많을수록 좋다"** — 최신 모델에선 과잉 과정지시가 오히려 성능을 떨어뜨린다(outcome-first).
4. ❌ **"AI가 만들고 AI가 검토했으니 배포해도 된다 / 프로토타입이 잘 돌면 그대로 프로덕션에 써도 된다"** — 도구 리뷰는 보조 신호일 뿐이고, 프로토타입과 프로덕션은 요구 수준이 다르다.
5. ❌ **"에이전트는 더 좋은(더 큰) LLM이다" / "ChatGPT에 질문하면 그게 에이전트다"** — 단발 질의응답은 LLM 사용이고, 도구를 스스로 반복 호출해 워크플로를 완수해야 에이전트다.

## 3. Topic-by-topic Findings

### Q1. 일반 LLM과 AI Agent의 근본적 차이
- **정의**: LLM은 입력 텍스트로 '다음 텍스트'를 생성하는 모델(부품). AI 에이전트는 그 LLM을 두뇌로 삼아 도구를 스스로 골라 쓰며 여러 단계를 판단·실행해 목표를 완수하는 시스템. 에이전트는 '환경 피드백을 받아 루프 안에서 도구를 쓰는 LLM'이다.
- **근거출처**: https://www.anthropic.com/engineering/building-effective-agents (2024-12-19) / https://developers.openai.com/api/docs/guides/agents (현행)
- **장점**: 하나의 개념(자율성·루프·도구)으로 세 도구를 통합 설명 가능.
- **한계**: 대표 정의 문헌(2024-12)은 창 밖. 다만 Managed Agents 문서(베타헤더 2026-04-01)가 동일 정의를 현행으로 확인.
- **초급자 표현**: "LLM은 똑똑한 자동완성 엔진, 에이전트는 그 엔진에 손발(도구)과 '끝까지 알아서 반복하라'는 지시를 붙인 프로그램."
- **슬라이드 한 문장**: "LLM은 '문장을 생성하는 모델', AI 에이전트는 그 LLM이 도구를 써서 스스로 여러 단계를 실행해 일을 끝내는 '시스템'이다."

### Q2. 에이전틱 코딩 vs 바이브 코딩 (정의·유행어 여부·관계·기획자 장단점)
- **정의**: 에이전틱 코딩 = AI를 '자동완성'에서 '자율 작업 수행자'로 끌어올린 개발 방식(공식 용어). 바이브 코딩 = 2025-02 Karpathy가 만든 비공식 신조어로, AI 생성 코드를 깊이 검토하지 않고 결과 위주로 받아들이는 사용 태도. 관계(교육용 정리): 셋은 동의어가 아니다 — '에이전틱 코딩'은 도구의 자율성 축, '바이브 코딩'은 사람의 검토 태도 축을 가리킨다. 셋을 엄격한 상하위 포함관계로 규정할 공식 근거는 없으므로 구분(≠)으로만 설명한다.
- **근거출처**: https://www.anthropic.com/research/claude-code-expertise (2026-06-16) / https://claude.com/blog/introduction-to-agentic-coding (2025-10-30) / https://spectrum.ieee.org/vibe-coding (2025-04-08) / https://arxiv.org/abs/2506.23253 (2025-06-29) / https://learn.microsoft.com/en-us/microsoft-for-startups/build/intro-agents (2026-04-14)
- **장점(기획자)**: 코드를 못 짜도 자연어 지시로 동작하는 프론트 프로토타입·PRD·디자인 초안을 빠르게 생성. '사람은 무엇을(what)·도메인 판단, 에이전트는 어떻게(how)' 역할 분담. Anthropic 40만 세션 분석상 성공을 예측하는 건 코딩 배경이 아니라 도메인 전문성.
- **한계(위험)**: 검증 없이 수용하면 '그럴듯하지만 틀린'·엣지케이스 미처리 결과(trust-then-verify gap). 프로토타입엔 적합하나 프로덕션엔 부적합, '기본기의 대체재가 아니다'.
- **초급자 표현**: "기획자는 메뉴와 손님을 정하는 사람, AI 에이전트는 주방에서 요리하는 사람. 맛을 보지도 않고(검증 없이) 손님상에 내면 탈이 난다."
- **슬라이드 한 문장**: "에이전틱 코딩(도구의 자율성)과 바이브 코딩(사람의 검토 태도)은 다르다 — 공식 문서는 'agentic coding/coding agent'를 쓰고, 'vibe coding'은 2025년 유행어다."

### Q3. 최신 프롬프트 엔지니어링 기준 (OpenAI GPT-5.5 / Anthropic Opus 4.8)
- **정의**: OpenAI(GPT-5.5, 2026-04-24 출시)는 outcome-first — 원하는 결과·성공기준·제약·출력형태를 먼저 적고, 경로가 중요할 때만 단계 지시. Anthropic(Opus 4.8, 2026-05-28)은 '맥락 없는 신입에게 설명하듯' 명확·구체 + 긍정 예시(<example> 태그) + XML 구조 + 역할 부여. 공통 뼈대는 지시·맥락·제약·형식·예시 + 작게 반복(평가셋으로 측정, 한 번에 하나씩).
- **근거출처**: https://developers.openai.com/api/docs/guides/prompt-guidance / https://developers.openai.com/api/docs/changelog (2026-07-06) / https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices / https://www.anthropic.com/news/claude-opus-4-8 (2026-05-28)
- **장점**: 세션 도구가 Codex(OpenAI 계열)라 OpenAI 기준이 특히 직접 적용. 초급자 6원칙은 두 회사 교집합이라 도구 비종속.
- **한계**: 가이드 '페이지'들은 발행일 미표기(확인불가). 대신 대상 모델 출시일(GPT-5.5 2026-04-24, Opus 4.8 2026-05-28)로 창 내임을 입증. text.verbosity·Structured Outputs·XML 등 세부는 도구별로 다르므로 실제 문서 확인 필요.
- **초급자 표현**: "프롬프트는 '우리 사정을 전혀 모르는 똑똑한 신입'에게 주는 업무지시서다. 마법 문구 암기가 아니라 명확함과 반복이 실력."
- **슬라이드 한 문장**: "'어떻게 하라'는 과정보다 '무엇이 좋은 결과인가'라는 결과·제약·출력형태를 먼저 명확히 적어라(OpenAI 2026-04, Anthropic 2026-05)."

### Q4. Context Engineering (정의·에이전트 중요성·구성·문서 관련)
- **정의**: 컨텍스트 엔지니어링 = 'LLM 추론 중 최적의 토큰(정보) 집합을 큐레이션·유지하는 전략들'. '어떤 단어를 쓸까'(프롬프트)를 넘어 '모델이 매 순간 무엇을 보게 할지'(시스템지침·도구·예시·대화기록·외부데이터)를 설계하는 프롬프트 엔지니어링의 다음 단계.
- **근거출처**: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (2025-09-29) / https://platform.claude.com/docs/en/build-with-claude/context-windows (현행) / https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization (2026-01-05) / https://agents.md/
- **장점**: 토큰 비용 절감, 모델 집중·정확도 유지, 멀티세션 지속성. prd.md·design.md가 '외부화된 컨텍스트'로 세션 간 의도를 전달.
- **한계**: 권위 있는 정의 원전은 모두 창 밖(2025-09~2026-01). 슬라이드에서는 '2025년 하반기~2026년 초 공식 정립된 개념'으로 시점을 정직하게 표기.
- **초급자 표현**: "프롬프트가 '질문 문장 다듬기'라면, 컨텍스트 엔지니어링은 '책상 위에 어떤 자료를 올려둘지 통째로 정리하기'다. 폴더에 파일이 있어도 대화에 올리지 않으면 모델은 그 존재를 모른다."
- **슬라이드 한 문장**: "컨텍스트 엔지니어링은 모델이 매 순간 무엇을 보게 할지(지침·도구·문서·대화기록·외부데이터)를 설계하는 일이다 — 더 많이 넣는 게 아니라 잘 고르는 것."

### Q5. Agent 지침 파일 (AGENTS.md / CLAUDE.md / Cursor Rules)
- **정의**: 코딩 에이전트가 매 세션/실행 시 '자동으로' 읽는 지속 지침·규칙 파일(HOW). 빌드·테스트·코드스타일·경로·커밋 규칙 등 '항상 지킬 방법'을 담는다. prd.md·design.md 같은 요구사항 문서(WHAT·WHY)와 로딩 방식·역할이 근본적으로 다르다.
- **근거출처**: https://developers.openai.com/codex/guides/agents-md / https://code.claude.com/docs/en/memory / https://agents.md/ / https://cursor.com/docs/rules
- **장점**: 자동 로드로 반복 입력 불필요, 버전관리로 팀 공유, 요구(WHAT)와 규칙(HOW) 분리.
- **한계**: 참고 컨텍스트일 뿐 하드 강제 아님(강제는 hook/permissions). 200줄 초과 시 준수율↓. Claude Code는 AGENTS.md를 직접 안 읽어 @import·symlink 필요. 공식 지침 문서 대부분 날짜 미표기(확인불가).
- **초급자 표현**: "규칙 파일은 도구가 켜질 때마다 자동으로 펼쳐 읽는 '사내 규정집', prd/design은 '이번 프로젝트 기획서'라 직접 가리켜야 반영된다."
- **슬라이드 한 문장**: "AGENTS.md·CLAUDE.md·Cursor Rules는 도구가 매 세션 자동으로 읽는 규칙 파일(HOW), prd.md·design.md는 직접 지목해야 하는 요구사항 문서(WHAT)."

### Q6. prd.md·design.md — 공식 필수인가, 실무·교육 패턴인가
- **정의**: prd.md·design.md는 OpenAI·Anthropic·Cursor 어디에도 없는 비표준·교육용 관례 파일명이다. 자동으로 읽히는 표준은 AGENTS.md·CLAUDE.md·.cursor/rules뿐. 단 '코딩 전에 요구·설계를 먼저 문서로 쓰는' 접근(Spec-Driven Development)은 공식적으로 체계화돼 있고, prd/design은 그 패턴의 교육용 별칭에 가깝다.
- **근거출처**: https://github.com/github/spec-kit (2026-07-07) / https://learn.microsoft.com/en-us/training/modules/spec-driven-development-github-spec-kit-greenfield-intro/ (2026-07-03) / https://kiro.dev/docs/specs/ (2026-06-25)
- **장점**: 요구/규칙 분리로 목표 명확화, 명세로 재현성·신뢰성↑, 마크다운·버전관리로 팀 리뷰 용이. (AWS Kiro는 design.md 파일명을 그대로 사용)
- **한계**: 공식 강제 파일명이 아니라 자동으로 읽히지 않으므로 반드시 지목/import. 표준 파일명이 없어(spec/requirements/product-brief 등) 팀 컨벤션 합의 필요.
- **초급자 표현**: "설계도를 그리고 나서 짓기. 공식 규격이라서가 아니라 에이전트가 딴 길로 새지 않게 돕는 검증된 습관이라 교육에서 쓴다."
- **슬라이드 한 문장**: "prd.md·design.md는 공식 필수 파일이 아니라 '코딩 전에 요구·설계를 먼저 쓰는' 실무 패턴(Spec-Driven Development)의 교육용 이름이다."
- *(가드레일 처리)*: 슬라이드·구두 설명에서 prd/design을 '업계 공식 표준 파일'로 단정하지 않되, "이건 표준이 아닙니다"라고 대놓고 부정하지도 않는다. "실습에서 쓰는 문서 패턴이고, 같은 원리를 GitHub·AWS가 spec.md/design.md로 정식 도구화해 뒀다"는 톤으로 처리.

### Q7. PRD·IA·User Flow·Design Spec이 프로토타이핑에 연결되는 방식
- **정의**: PRD='무엇을 왜'(문제·목표·성공기준), IA=화면·정보구조, User Flow=이동 순서, Design Spec=화면·UI 기준. 네 문서를 하나의 표준 파이프라인으로 묶은 '최신 공식 정설'은 확인되지 않았다. 다만 최근 공식 자료가 뒷받침하는 흐름은 '명세(PRD 성격) → 디자인 기준 → 프로토타입·코드 생성 → 핸드오프'의 스펙 주도 흐름이다.
- **근거출처**: https://www.anthropic.com/news/claude-design-anthropic-labs (2026-04-17) / https://github.com/github/spec-kit/blob/main/spec-driven.md (현행) / https://www.nngroup.com/articles/ux-deliverables-glossary/ (2024-08-09, 참고)
- **장점**: Claude Design(2026-04)이 '디자인 시스템(=Design Spec 코드화) 자동 적용 → 인터랙티브 프로토타입 → Claude Code 핸드오프'라는 창 내 실사례를 제공.
- **한계**: 네 문서를 정확히 4단계로 연결한 최신 공식 정설은 확인 불가 — 슬라이드에서 '정설'이 아니라 '실무 예시'로만 제시. UX 용어 정의 원전(NN/g)은 2024-08로 창 밖.
- **초급자 표현**: "화면 만들라고 하기 전에 '무엇을 왜'(prd)와 '화면·UI 규칙'(design)을 먼저 글로 정하면 에이전트가 일관되게 만들고 검증도 쉬워진다."
- **슬라이드 한 문장**: "최근 공식 흐름은 '무엇을 왜(PRD)'와 '화면·UI 기준(Design Spec)'을 먼저 정의해 에이전트에 입력하고, 반복 수정으로 프로토타입을 만든 뒤 코딩 에이전트로 넘기는 것이다(Claude Design 2026-04)."

### Q8. AI 생성 코드·프로토타입의 검증
- **정의**: 대원칙은 '에이전트가 제안하고 사람이 승인·검증한다(Human-in-the-loop)'. 최근 흐름은 매 액션 승인에서 '별도 리뷰 에이전트 + 사람의 모니터링·최종 승인'으로 이동. 방법: ①테스트·정적분석·보안 스캔 자동화 → ②의존성·환각 API 확인 → ③요구사항 부합 검토 → ④사람 리뷰, 그리고 evals(Outcome/Process/Style/Efficiency 4축, 10~20개 프롬프트)로 산출물 검증.
- **근거출처**: https://alignment.openai.com/auto-review/ (2026-04-30) / https://docs.github.com/en/copilot/tutorials/review-ai-generated-code (현행) / https://github.blog/changelog/2026-06-25-copilot-code-review-analysis-depth-and-efficiency-updates/ (2026-06-25) / https://developers.openai.com/blog/eval-skills (2026-01-22)
- **장점**: 소프트웨어는 출력을 테스트·비교·리뷰할 수 있어 감독에 적합. 큰 벤치마크 없이 10~20개 프롬프트로 회귀·개선을 잡아낼 수 있다.
- **한계**: 자동 리뷰는 '보안 보장이 아님'(OpenAI 명시), AI 리뷰 도구도 환각·누락. evals·검증루프·보안리뷰 원문 일부는 창 밖(2025~2026-01)이라 '공식 방법론'으로만 소개하고 최신성은 Auto-review(2026-04)·Copilot 창로그(2026-06)로 보강.
- **초급자 표현**: "'좋아 보인다'로 끝내지 말고 '앱이 실행되나? 요청한 단계를 따랐나? 규칙을 지켰나?'를 매번 같은 방식으로 확인하는 게 evals다."
- **슬라이드 한 문장**: "AI가 짠 코드는 '테스트·보안 스캔 자동화 → 의존성·환각 API 확인 → 요구사항 대조 → 사람 리뷰' 순으로 점검하고, AI 리뷰 도구의 지적조차 사람이 다시 검증한다."

### Q9. AI Agent 안전성·권한관리 (초급자용)
- **정의**: 에이전트가 위험한 건 '답만 하는' 챗봇과 달리 실제로 행동하기 때문이다. 세 행동 = (1) 파일 수정 (2) 명령 실행 (3) 외부 도구·API 연결. 세 도구(Codex·Claude Code·Antigravity)는 동일 안전 모델을 공유한다: 기본 읽기 위주, 상태 변경은 명시적 승인, 쓰기는 작업폴더 한정, 네트워크는 기본 차단/승인 게이트.
- **근거출처**: https://developers.openai.com/codex/concepts/sandboxing / https://developers.openai.com/codex/agent-approvals-security / https://code.claude.com/docs/en/security / https://codelabs.developers.google.com/getting-started-google-antigravity / https://developers.openai.com/codex/changelog (2026-07-08)
- **장점**: 세 도구 안전 모델이 동일해 하나의 개념으로 통합 설명 가능. 샌드박스는 승인 피로를 줄이면서 안전 유지(Anthropic 측정상 승인 프롬프트 84%↓).
- **한계**: 샌드박스는 위험 감소 장치일 뿐 완전 격리 아님(TLS 미검사·도메인 프론팅 우회). danger-full-access/--dangerously-skip-permissions를 켜면 모든 보호가 무력화. 공식 문서 대부분 날짜 미표기(창 내 앵커는 Codex Changelog 하나).
- **초급자 표현**: "챗봇은 틀려도 '틀린 답'이지만, 에이전트는 틀리면 '틀린 행동'(파일 삭제·잘못된 명령·데이터 전송)을 한다. 기본값을 그대로 두고 승인창을 '읽고' 눌러라."
- **슬라이드 한 문장**: "에이전트는 '말'이 아니라 '행동'한다 — 파일 수정·명령 실행·외부 연결은 반드시 내가 승인하고, 비밀키·외부 DB·배포·승인 우회 모드는 초급 세션에서 절대 하지 않는다."

### Q10. 90분 초급 세션에서 다룰 것 vs 뺄 것
- **정의**: OpenAI Codex Best practices는 '처음이면 기본 권한으로 시작, 신뢰가 쌓인 뒤에만 완화'와 프롬프트 4요소(Goal·Context·Constraints·Done-when), plan→review 루프를 핵심 습관으로 제시하고, AGENTS.md·skills·automation은 '필요가 분명해진 다음 단계'로 배치한다.
- **근거출처**: https://developers.openai.com/codex/learn/best-practices / https://developers.openai.com/codex/changelog / https://code.claude.com/docs/en/security
- **반드시 다룰 것**: ①prd.md(무엇을·왜) ②design.md(화면·구조·상태) ③Mock Data 프론트 프로토타입 생성·미리보기 ④안전 기본기(기본 권한 유지, 승인창 읽기, 비밀키·외부 API·배포 금지) ⑤plan→review 반복.
- **참고로만·실습에서 뺄 것**: AGENTS.md·CLAUDE.md·커스텀 rules·hooks·skills·subagents·MCP 외부연결·인증·결제·DB·배포. ('있다'만 한 장 소개)
- **한계**: '90분에 정확히 무엇을 빼라'는 문항별 공식 커리큘럼 문서는 없다. OpenAI의 '단계적 도입' 원칙 + 세션 목표(완성앱 아님, mock 프로토타입, 핵심파일 prd/design)에 근거한 합리적 편성임을 명확히.
- **초급자 표현**: "필요한 건 코드 문법이 아니라 '무엇을·왜를 에이전트가 알아듣게 문서로 적는 힘'. 자동화 장치들은 반복 작업이 생겼을 때 배우면 된다."
- **슬라이드 한 문장**: "90분 핵심은 prd.md·design.md로 '무엇을 만들지'를 정의하고 mock 프론트 프로토타입까지 완주하는 것 — 나머지 고급 기능은 '있다'만 소개한다."

## 4. 적용 가이드

### 반드시 포함할 개념 (본론 핵심)
1. LLM vs 에이전트 = '부품 vs 시스템', 에이전트 루프(도구 호출→결과→판단 반복) — 1~2주차 What/Why와 연결.
2. 에이전틱 코딩 = '자동완성을 넘어선 자율 작업 수행자' / 바이브 코딩은 유행어라는 톤 처리.
3. 초급자 프롬프트 6원칙(결과·맥락·제약·형식·예시·반복).
4. prd.md(WHAT·WHY)·design.md(IA·User Flow·상태·UI 기준) 작성 — 세션 뼈대.
5. 안전 기본기(세 행동 승인, 기본 권한 유지) + 검증 습관(실행·흐름·대조).

### 5분 이내로만 언급할 개념
- Context Engineering(컨텍스트 = 모델의 작업기억, 더 넣는 게 아니라 잘 고르기) — 개념만.
- AGENTS.md/CLAUDE.md/Cursor Rules가 '자동으로 읽히는 규칙 파일'이라는 사실 한 장(prd/design과 대비용).
- Spec-Driven Development(GitHub Spec Kit·AWS Kiro)가 prd/design과 같은 원리라는 근거 한 장.
- Google Antigravity·Codex 접근 방식(도구 소개).

### 제외할 개념 (실습 범위 밖)
- hooks / skills / subagents / MCP 외부 연결 / 커스텀 rules 세부.
- DB·API·로그인·회원가입·결제·지도·알림·배포·예외상태 구현.
- reasoning effort·text.verbosity·Structured Outputs·XML 태그 등 파라미터 세부.
- evals API·CI 자동화·보안 스캐너(CodeQL/Dependabot) 실습.

```
project/
  prd.md          # 무엇을·왜 (문제·타깃·핵심기능·성공지표·User Flow 요약)
  design.md       # 화면 목록·IA·레이아웃·컴포넌트·상태(Empty/Loading/Error)·UI 기준
  index.html      # Mock Data 프론트 프로토타입 (HTML/CSS/JS만)
  /assets         # mock 데이터·이미지
```
- prd.md·design.md는 자동으로 읽히지 않으므로 프롬프트에서 "prd.md·design.md를 읽고 index.html을 만들어줘"라고 명시적으로 지목.

### prd.md 항목 (Codex 4요소 + 1~6주차 기획개념 매핑)
- **개요/목표(Goal)**: What(무엇을)·Why(왜) — 1주차.
- **타깃 사용자(Context)**: Who·사용 시나리오 — 2~3주차.
- **핵심 기능(범위)**: MVP 기능 3~5개 + 제외 범위(Scope) — 4~5주차.
- **User Flow**: 주요 이동 순서 — 3주차.
- **성공 기준/검증(Done-when)**: 성공지표·검증 방법 — 6주차.
- **제약(Constraints)**: Mock Data 프론트만, DB/로그인/결제/배포 제외.

### design.md 항목
- 화면 목록(IA) / 화면별 레이아웃·컴포넌트 / 상태 정의(Empty·Loading·Error) / 색·타이포·간격 등 UI 기준(Design Spec) / 반응형 규칙.

### 문서 사용 vs 미사용 비교 데모 방식
- **미사용**: "쇼핑 앱 만들어줘" 같은 막연한 프롬프트 → 에이전트가 미명시 요구를 '추측'해 엉뚱하거나 들쭉날쭉한 결과. (GitHub Blog 근거: 막연한 프롬프트 = 수천 개 요구 추측)
- **사용**: 동일 아이디어를 prd.md·design.md로 먼저 정의 → 지목 → 일관된 프로토타입. 두 결과를 나란히 띄워 '문서가 도면 역할'임을 체감시킨다. (근거: Spec Kit·MS Learn의 '명세우선 vs vibe coding' 비교)

## 6. 불확실·확인 불가

### 최근 3개월 내 신뢰 자료가 없는(또는 창 밖) 주제
- **LLM/에이전트·에이전틱 코딩·컨텍스트 엔지니어링의 '정의' 원전**: 대표 문헌 다수가 창 밖(Building effective agents 2024-12-19, agentic coding 2025-10-30, context engineering 2025-09-29). 정의 자체는 안정적·공식성 높으나, 슬라이드에서는 "2024년 말~2026년 초 공식 정립된 개념"으로 시점을 정직하게 표기할 것. 창 내 보강 근거는 Claude Code 실사용 연구(2026-06-16), Managed Agents(베타 2026-04-01), Opus 4.8(2026-05-28), GPT-5.5(2026-04-24).
- **PRD·IA·User Flow·Design Spec을 하나의 파이프라인으로 묶은 최신 공식 정설**: 확인 불가. Claude Design(2026-04)은 'Design Spec→프로토타입' 구간만, spec-kit은 발행일 미표기, NN/g 용어 정의는 2024-08. → 4단계 연결은 '실무 예시'로만 제시, 정설로 단정 금지.
- **UX 용어(PRD·IA·Design Spec)의 최신 표준 정의**: NN/g 글에도 해당 항목이 없어 최근 공식 근거로 제시 불가.
- **'90분에 무엇을 빼라'는 문항별 공식 커리큘럼**: 존재하지 않음. OpenAI 단계적 도입 원칙 + 세션 목표 기반 합리적 편성임을 명시.

### 공식 vs 보조 충돌 / 주의 주제
- OpenAI의 'A practical guide to building agents'(openai.com 계열) 및 여러 index/help 페이지는 WebFetch 403으로 접속 실패 → 전면 배제. 정의는 접속 성공한 developers.openai.com 문서로 대체 확인(취지 동일).
- 세션 도구 문구('Vibe Coding')를 공식 표준처럼 말하지 말 것 — 공식 용어는 'agentic coding / coding agent'다. 단 "이건 표준이 아닙니다"라고 대놓고 부정하지 말고 톤으로 처리(가드레일).

### 추가 검증 필요
- **날짜 미표기(확인불가) 공식 문서 다수**: tool-use·prompt·memory·sandbox·pricing·CLI 문서 등은 '살아있는 현행 문서'지만 페이지에 발행/수정일이 없다. 본문 근거로 쓰되 "2026-07-08 접속 시점의 현행 공식 문서"임을 전제로만 사용(핵심 최신성 앵커는 Codex Changelog 2026-07-08, GPT-5.5 Changelog 2026-07-06, Spec Kit 2026-07-07, Copilot 창로그 2026-06 등 날짜 확인 자료).
- **arXiv 2606.31159(2026-06-30)**: 창 내지만 페이지에서 저자 소속 기관 라인을 직접 확인하지 못함 — 인용 시 '소속 미확인' 유의.
- **ICSE 2026 보안 결과·ACM 'Vibe Coding' TechBrief·Google Cloud 'What is vibe coding'**: 검색 스니펫에만 등장하거나 403 차단으로 원문 미확인 → 인용에서 제외.
- **Antigravity 2.0 세부**(CLI 이관·AI Ultra $100 티어)·**Codex '5시간 창 한도'**: 후속 fetch에서 직접 문구 확인이 안 된 항목이 있어, 슬라이드에 수치로 단정하지 말고 '무료 프리뷰로 시작 가능'·'Go 플랜에 포함' 수준으로만 표기.

### 절대 단정하면 안 되는 표현
- "prd.md·design.md는 공식 표준/필수 파일이다" (아님 — 교육용 관례).
- "이 4단계(PRD→IA→User Flow→Design Spec) 파이프라인이 업계 공식 정설이다" (확인 불가 — 실무 예시).
- "샌드박스만 켜면 100% 안전하다" / "에이전트는 프로젝트 폴더 밖은 절대 못 건드린다"(읽기는 컴퓨터 전체 가능, full-access 시 경계 소멸).
- "AI 생성 코드는 최신이라 보안이 기본으로 안전하다" (실증연구상 취약점 자주 포함·모델 과신).
- "Vibe Coding은 정식 개발 방법론/업계 표준이다" (비공식 신조어).
- 이 프로토타입은 '완성 서비스'다 (Mock Data 프론트 초안일 뿐).
